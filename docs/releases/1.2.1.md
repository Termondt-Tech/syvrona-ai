# [1.2.1] - 2024-06-25

## Overview

This release introduces robust spam protection for user authentication and registration workflows, including both honeypot field implementation and the integration of hCaptcha for human verification. Administrators now have full control to enable or disable hCaptcha globally via configuration/environment variables. This release also includes code improvements for maintainability and best-practice compliance.

## Enhancements

- **Anti-Bot Signup & Login Protections**
  - Implemented a _honeypot_ hidden field on both signup and login forms to block basic automated bot submissions. If the field is filled, the attempt is silently rejected and logged.
  - Integrated [hCaptcha](https://www.hcaptcha.com/) as an advanced anti-spam and anti-bot solution on user signup and login forms.
  - hCaptcha settings (enable/disable, site/secret keys) are now fully configurable through environment variables and the Flask config class.
  - hCaptcha widget is conditionally rendered on forms only if enabled in config.
  - Backend routes conditionally verify hCaptcha based on config, ensuring seamless developer testing and staged rollouts.

- **Configuration Enhancements**
  - Added `HCAPTCHA_ENABLED`, `HCAPTCHA_SITE_KEY`, and `HCAPTCHA_SECRET_KEY` to the `Config` class.
  - hCaptcha activation is controlled via the `HCAPTCHA_ENABLED` environment variable (`true`/`false`).
  - Added global context processor to inject the `HCAPTCHA_ENABLED` value into all templates.

- **Template and UI Updates**
  - Updated signup and login templates to conditionally render the hCaptcha widget only when enabled, maintaining clean UI/UX.
  - Retained the original honeypot anti-spam field, fully hidden from legitimate users.
  - All new code adheres to HTML best practices—semantic markup, accessible forms, and security-minded attribute handling.

- **Backend Logic Updates**
  - Signup and login POST routes now check for both honeypot completion and (if enabled) hCaptcha verification before creating a user session or Stripe customer.
  - Failure of either anti-bot check results in a generic error message and safe redirect, without exposing system details to bots.
  - Logging enhanced for spam and bot activity detection.

- **Documentation & Policy**
  - Privacy Policy updated to explicitly disclose hCaptcha usage, with accessible links to hCaptcha's Privacy Policy and Terms of Service, following industry best practice.
  - Example privacy policy section provided for compliance and transparency.

## Technical Implementation Details

- **Honeypot Field:**
  - Added a hidden text input (`middle_name`) to both the signup and login forms.
  - POST routes check if the honeypot field is filled and block the attempt if so.

- **hCaptcha Integration:**
  - Utilized the `flask-hcaptcha` extension for widget rendering and server-side verification.
  - Added `HCAPTCHA_ENABLED` boolean to config for full environment-driven enable/disable support.
  - Injected `HCAPTCHA_ENABLED` into Jinja templates via a context processor.
  - Used `{% if HCAPTCHA_ENABLED %}{{ hcaptcha }}{% endif %}` for conditional widget rendering.
  - Only call `hcaptcha.verify()` in routes if enabled.

- **Config Class:**
  - `HCAPTCHA_ENABLED = os.getenv("HCAPTCHA_ENABLED", "false").lower() == "true"`
  - Keys read from `.env` file for local and production parity.

- **Template & Code Best Practices:**
  - No use of deprecated Jinja filters (e.g., `escapejs`).
  - Inline JS in templates kept to minimal, linter-friendly patterns.
  - Optionally suggested use of data attributes and delegated JS for larger refactors.

- **Developer/DevOps Notes:**
  - hCaptcha can be enabled or disabled instantly by changing `.env` or environment configuration, with no code changes required.
  - Logging records spam/bot activity for later analysis.

## Upgrade Notes

- Add or update the following environment variables as needed:
  - `HCAPTCHA_ENABLED=true` (or `false`)
  - `HCAPTCHA_SITE_KEY=...`
  - `HCAPTCHA_SECRET_KEY=...`
- Review and adjust privacy policy and user-facing documentation to reflect new protections.

## No Schema Changes

This release does **not** introduce any database schema changes or migrations.

## Known Issues and Future Work

- Linter warnings on inline JS using template variables may persist due to template rendering. These are cosmetic and do not affect runtime.
- Recommend future migration of all JS event handlers to data-attribute patterns for full linter and IDE compatibility.
- Ongoing monitoring of spam/bot activity and further tuning of hCaptcha settings as user base grows.
